# 一起到

用自然语言收集条件，用脚本计算和排序，用可核实的数据解释方案。此 Skill 是规划工具；不执行下单或付款。

## 首次使用

定位本 Skill 根目录，所有命令在该目录执行。需要 Python 3.9+；Python 无第三方依赖。真实查询还需要官方 `flyai` CLI 和用户通过平台密钥管理配置的 FlyAI 凭证。先执行 `python3 scripts/yiqidao.py --help`。安装方式和运行说明见 [README.md](README.md)。

需要检查安装完整性时可做离线自检（虚构数据，不可预订）；用户要求真实查询时不要先跑演示代替：

```bash
python3 scripts/yiqidao.py plan --request examples/offline_replay.json --mode fixture --cache-dir examples/fixtures --output outputs/demo.md --save-state outputs/demo-state.json
```

## 收集与校验

确认每人名字、出发城市、出发和返程日期窗、预算、允许的交通方式、单程或往返时长上限；确认最多 5 个候选城市、住宿晚数、房间数、房间分配和最少共同停留小时数。不要默默放宽用户限制。原型只支持飞机/火车和国内短途。

普通聊天先用一轮简短问题补齐缺失的日期、成员预算/交通偏好和住宿分房；已有信息不重复问。用户没选城市时可提出2–3个候选及理由，请用户确认搜索范围，不把建议当既定条件。“玩两天”必须澄清具体日期和住几晚。用户确认后直接查询，不要求用户填写JSON或执行命令。报价未齐时也应先给交通比较和酒店/景点候选，不陷入反复追问。用户已给出具体日期和候选城市时，按该范围执行，不再询问是否浮动日期或是否查询这些城市；年份可按当前年份明确记录，不作为重复确认的阻塞项。没有提供到家硬截止时可说明暂未设置，不阻塞查询。只有用户表示房型有硬要求时才追问双床或大床。共同停留时长必须按班次时刻和缓冲计算，不能仅凭住宿晚数推断必须早到晚走；两晚不等同于30小时，也不说明30小时难以满足。

把条件写为 `outputs/request.json`，字段参考 [examples/hangzhou_3cities.json](examples/hangzhou_3cities.json)。日期为北京时间；不要把示例日期当用户日期。只需 2–4 位成员；住宿按人数平均分摊，房间分配用于校验。预算计算仅含已知长途交通与住宿，餐饮、市内接驳等另列待核实。

```bash
python3 scripts/yiqidao.py validate --request outputs/request.json
```

退出码 2 时补问阻塞信息；4 时修复输入或配置；校验通过后再查询。规划退出码 5 表示已有交通候选，但住宿/票价等仍需确认，并非运行失败。

## 真实规划

先用 1 个候选城市验证接口，正常后扩大到 2–3 个。不要并行查询或连续循环重跑。

```bash
python3 scripts/yiqidao.py plan --request outputs/request.json --mode live --cache-dir .cache --timeout 30 --max-seconds 300 --max-calls 80 --verbose --output outputs/result.md --save-state outputs/latest-state.json
```

默认查询最多3组可行日期和返回的交通候选，用--max-date-pairs可调整。未查完且无候选结果时退出码6/search_incomplete，不能据此说无解。搜索范围内比较已知费用，不保证整个市场最低。仅用户要求且接口正常时增加 `--time-optimal` 扩大时刻查询。

默认整房住宿候选会排除名称含青年公寓、青旅、床位等提示的结果；如果没有剩余候选，应补查或向用户说明，不能把床位价当双人房报价，也不能凭名称保证房型适合。酒店搜索展示价不得作为整房每晚报价参与费用计算。遇到 `needs_confirmation`，展示交通候选和需确认事项，不能宣称完整方案已满足预算。仅用户明确核实报价、日期和人数后才能填写 `hotel_quote.confirmed=true`；字段见 [docs/hotel-quote-rules.md](docs/hotel-quote-rules.md)，不得由模型推测或伪造。共同停留默认扣除到站后60分钟和离站前90分钟缓冲，可按用户条件调整。

换乘风险由脚本按每段到达/下一段出发计算：同站火车少于30分钟、同机场飞机少于120分钟，或跨站/站点缺失时标待确认。这是保守初筛，不是承运人标准或可衔接保证；费用和硬限制允许时优先无上述风险的组合。保留风险组合时明确说明，不承诺可直接预订。普通聊天摘要也必须保留换乘间隔和风险，不只抄总时长。

住宿缺报价时邀请用户直接回复：酒店名称、房型、城市、入住/退房、每房每晚含税价、每房人数及来源。可先只提供部分资料，继续追问剩余关键项；未齐时保留待确认，不能伪造confirmed。深夜或跨日到店需另问房间保留和夜间入住。引用报价前复述需确认的具体酒店、日期、人数和金额；仅用户明确确认后填写hotel_quote。库存与退改另行核实，报价确认不等于下单。

结果要求：展示往返交通、每人已知费用与缺失项、住宿分摊、共同停留时间、最辛苦成员、来源与原始查询时间。价格缺失不能算免费；有失败不能说条件无解；缓存不能说刚刚实时查询；测试数据不能用于报价或参赛实测证明。库存、房型人数、位置、退改与最终价格须用户在飞猪页面确认。不要把 `budget_state=ok` 解释为整个旅行总费用在预算内。

遇到 401、403、429、451 或总时限时本轮停止真实请求。保存结果并说明失败原因；不要改变身份、绕过限制或无限重试。无可行结果且查询失败时退出码 4，不等同于确定无解（退出码 3）。

## 续接与修改

接续前读取 `outputs/latest-state.json`，里面保存完整请求和方案。实际续跑：

```bash
python3 scripts/yiqidao.py plan --resume-state outputs/latest-state.json --cache-dir .cache --output outputs/result.md
```

修改条件时从旧状态提取 `request`，只改用户指明的字段，保存为新请求再 `validate` 和 `plan`。实时缓存默认有效 15 分钟；过期重新查，保留原查询时间。需要历史回放时显式使用 `--mode fixture --cache-dir <录制目录>`，该模式绝不联网。不要用历史回放声称现在可以买。

结束时记录已完成内容、失败查询、下一步、状态和结果路径。用户要求导出续接包时，把当前 request、状态、结果、工作说明和必要代码保存到用户可下载位置；私有缓存单独处理，不混入公开作品包。不要输出密钥、配置文件或真实身份信息。参赛准备见 [docs/upload-and-resume.md](docs/upload-and-resume.md)。

整体逻辑与范围限制见 [docs/logic-audit.md](docs/logic-audit.md)。特别注意：完整日期窗缺失时必须补问；到家硬截止需计入home_buffer_minutes（默认60分钟）；请求/有效缓存续跑不等于恢复云端沙箱。
